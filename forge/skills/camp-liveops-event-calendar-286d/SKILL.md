Use when monetisation.md must include an event calendar or offer schedule.

1. Define the cadence layers first: always-on offers, weekly rotation, monthly feature, seasonal/holiday beat, and game-specific beats (updates, anniversaries). Name the layer each event belongs to.
2. Place anchor events on the platform calendar (Steam seasonal sales, Quest store features, major holidays in your top markets). These are fixed; everything else is scheduled around them.
3. Apply spacing rules: minimum gap between discounted events on the same SKU (no more than one price-changing event per SKU per fortnight), a discount floor (never below X% off the anchor price without a stated reason), and no two events targeting the same segment in the same week.
4. For each event, write one row: dates (UTC), SKU/offer, segment targeted, price/discount, expected uplift assumption (with basis), and the one KPI it is judged on (units, revenue, conversion, reactivation).
5. Give every event a pre/post measurement window (at least 3 days before/after) so uplift can be checked against the assumption later.
6. Sanity-check the whole calendar: revenue by month is spread, not stacked on one event; the strongest discount is reserved for the biggest-traffic window; at least one event per month targets lapsed players and one targets payers.

Before handover, verify: (a) every event row has dates, offer, segment, discount, assumed uplift and KPI; (b) no SKU has two overlapping events; (c) discount floors hold; (d) monthly revenue in the calendar sums to the revenue model; (e) assumptions are marked as measured, comparable-derived or assumed.

Common mistakes: stacking events so discounts become the expected price; setting uplift assumptions with no basis; forgetting time zones on dates; an event calendar that contradicts the price list.
