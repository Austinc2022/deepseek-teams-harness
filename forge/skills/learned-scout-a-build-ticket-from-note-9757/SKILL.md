---
name: learned-scout-a-build-ticket-from-note-9757
description: Whenever you are asked to scout methods/skills for a multi-turn build ticket whose stated obstacle is a turn/time limit or a lost run, and the ticket's work folder already exists.
---

1. Read the ticket's NOTES.md (and rc/NOTES.md) FIRST, before researching anything. The checkpoint lines are the ground truth for what actually landed; the brief is only a plan.
2. Count the checkpointed steps and read the LAST one. Determine whether the build is (a) not started, (b) partially built, or (c) essentially complete with only the report/verification missing. Most "the turn ran out of time" tickets are case (c).
3. If case (c), the methods brief must lead with "report now from NOTES.md + verify", not with build methods. The named obstacle is a symptom (reporting left to the end), not the real work.
4. For the named obstacle (turn/time limit before reporting), give the concrete counter-measures measured from the run: checkpoint one NOTES line per landed step; launch long real-browser runs DETACHED (nohup) and do docs/report while they run; write the report incrementally, not only at the end.
5. Only THEN research domain state-of-the-art (WebXR lifecycle, audio-clock scheduling, headless evidence, failing-control proofs) to fill genuine gaps.
6. Pick local skills that map to the distinct required deliverables (browser evidence, XR lifecycle test, failing-control proof), at most 3, best first. Pick at most 2 GitHub SKILL.md for the domain gap local skills do not cover. Keep skills read-only reference.
7. Ground every number you cite in a NOTES.md line or a knowledge fact; label strength measured/simulated/argued.
