name: camp-tc-qa-automation-spec-derive-68eb
description: Building an automated test suite for a shipped module where the spec promises must be verified honestly and known defects must surface as a red build rather than be hidden.
---

1. Read the spec and the shipped module side by side; derive every expected value by hand (score totals, boundary states) and note spec ambiguities — pick one reading, apply it consistently, and state it in the report.
2. Assert the SPEC, never the implementation. If shipped code deviates, keep the assertion strict so the suite fails — label the test with the violated promise (e.g. "SPEC#5 ... (KNOWN DEVIATION - expected FAIL)") but never weaken, skip, or mark it expected-fail. Add one test pinning user-visible impact (e.g. inflated score total) plus boundary pins showing exactly where behaviour starts/stops matching, so the defect is localized.
3. Unit suite: Node's built-in `node:test` + `node:assert/strict` — zero dependencies, no network. One test per spec promise; include result-object shape, post-end immutability, and reset semantics. Note when a value is not exposed by the public result (observe documented public fields instead).
4. Smoke suite: a driver script that loads the shipped module via absolute path from `__dirname` and plays a short deterministic session, printing a JSON timeline; a test spawns it with `spawnSync(process.execPath, ...)` so the module loads in a FRESH process. Keep the smoke session below any known defect boundary so it tests lifecycle independently. Assert exit code, empty stderr, and every checkpoint.
5. Runner: `run-tests.sh` with `set -u` (not `-e`) — run each suite, capture each exit code in a variable, print every code and a summary, exit non-zero if any suite fails. Wire `npm test` to it. Check `node --test <dir>` works on the installed Node first; if it errors "Cannot find module", use shell globs `node --test tests/**/*.test.js`.
6. Report (`test-report.md`): verdict up top; table of commands actually run with exit codes; exact assertion output for every failure; a quantified defect report (where, what, user-visible impact, what still holds); which spec promises were verified vs not verifiable with the given files (missing product files are listed as unverifiable — never fabricated); how-to-run section. Finish with an integrity check that fixtures were never modified (`git status --porcelain -- <fixtures>`).
7. Mistakes to avoid: letting a red suite hide which assertions are genuine defects vs broken tests (localize with boundary pins); asserting implementation details that the spec does not promise; fabricating stubs for undelivered product files; claiming unrun commands in the report.
