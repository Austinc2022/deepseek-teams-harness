# Claims: source status and consumer-copy fitness

Every factual assertion in listing copy, bullets, briefs and rationales gets **two independent judgments**. Never collapse them into one.

## 1. Claim inventory
Extract every assertion, including fact-adjectives: "glowing", "72 fps", "15 minutes", "subtitles", "works with controllers", "calm 10-minute escape". If a reader could test it and it might not hold, it is a claim.

## 2. The two calls per claim
- **Source status** — exactly one of:
  - **PLAN-SUPPORTED**: the approved plan states it or contains it as target-segment / positioning language (plan phrases about audience, session length, tone, price anchor count as supported, not invented).
  - **BUILD-SUPPORTED**: the build facts / QA gate state it.
  - **UNSUPPORTED**: neither source.
  - **CONTRADICTED**: a source says otherwise (e.g. measured playtime differs from copy) — flag the mismatch and prefer the measured figure in copy.
- **Consumer-copy fitness** — exactly one of: fits a player-facing field; fits only with an explicit scope/qualification ("desktop browser only", "may not work on all headsets"); or must not appear in player-facing copy at all.

## 3. Standing exceptions
- **Performance and hardware claims** (fps, resolution, battery, device coverage, load times): even when a build fact states them, they are unverified *in-platform* claims. Do not clear them for player-facing store bullets — flag them for owner verification and store dashboard preview.
- **Buyer-facing copy uses buyer language**: no QA/statistical jargon ("median playtime", "fps", "p95"). Translate to what the player experiences, or keep the metric in the notes only.

## 4. Never ship what you flagged
Any defect you note in a notes section must be fixed or explicitly qualified **in the consumer copy itself, in the same deliverable**. A self-flagged unsupported claim or jargon term left unqualified in the shipped copy loses points twice.

## 5. Descriptor fidelity
When reporting what a document, image or fact sheet says, use its own words or a clear hedge ("described as translucent, coloured magenta"). Never intensify (translucent → glowing, outline → glow) or add adjectives. Cite only what the source states, and note when it mentions something only in passing rather than asserting it.

## 6. Final numeric self-consistency pass (before you answer)
- Recompute every derived number: percentages, discounts, VAT/FX nets, character counts.
- Check every price or figure against your own stated bands, floors and limits; if a figure falls outside, acknowledge and justify it in the same sentence.
- Discount or offer windows are fixed, time-boxed mechanics (start and end dates), not ranges.
- Label soft inferences ("pricing at the floor captures volume") as inference, not evidence.

## 7. Action-checklist completeness
Owner/submission checklists must enumerate the full action sequence end to end as explicit steps: dashboard entry → listing preview/QA review → fix loop → submit for review → owner sign-off gate. Every rubric-relevant dashboard item appears as its own row.

## Common mistakes
- Clearing a verified performance number for store bullets because the build fact exists.
- Rejecting plan segment phrasing as "invented" because it is not a build fact.
- Noting a defect in notes and leaving it in the copy.
- Stating a percentage you did not recompute, or a range where an owner needs a date.
